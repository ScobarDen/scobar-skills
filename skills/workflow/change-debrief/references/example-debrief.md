# Разбор: `feature/ORD-412-order-status`

> 11 файлов · база `origin/dev` · 3 коммита + незакоммиченное рабочее дерево

## Суть

Экран заказов ходил в API сам: компонент дёргал `fetch`, получал DTO бэкенда и рисовал его поля напрямую. Теперь между ними стоит `OrderListViewModel` — он грузит, маппит DTO в доменную модель и отдаёт наверх готовое состояние. Повод был конкретный: бэкенд переименовал `status_code` в `state`, и починка этого поля потребовала правок в четырёх компонентах вместо одного.

## Карта изменений

- **Появился слой view-model** — `src/modules/orders/viewmodel/OrderListViewModel.ts`: загрузка, состояние запроса, маппинг.
- **DTO перестал выходить за границу модуля** — маппер `toOrder()` в `viewmodel/mappers.ts` единственный, кто знает форму ответа бэкенда.
- **Компоненты стали пассивными** — `OrderList.tsx` и `OrderRow.tsx` больше не знают ни про `fetch`, ни про поля API; принимают `Order` и колбэки.
- **Статус заказа стал одним union-типом** вместо трёх булевых флагов (`isPaid`, `isShipped`, `isCancelled`).
- Плюс 4 файла рутины: импорты, переименования, обновлённые сторисы.

## Главные решения

### 1. Маппинг DTO живёт в одном месте, а не в компонентах

**Выбрал:** единственная функция `toOrder(dto: OrderDto): Order`, через которую проходит весь ответ бэкенда.

**Почему:** форма ответа API — это чужая территория, её меняют без нас. Пока DTO расходился по компонентам, каждое переименование поля на бэкенде превращалось в раскопки по всему дереву — собственно, тикет ORD-412 про это и был. Теперь у чужого контракта ровно одна точка входа, и правка живёт в одном файле.

Это правило проекта, а не общая идея: `CLAUDE.md` в корне требует «UI не видит DTO» (строка про границы модулей), и соседний модуль `modules/billing` уже устроен так же — `billing/viewmodel/mappers.ts:14`.

**Отказался:** от маппинга прямо в хуке запроса. Короче на файл, но тогда маппер невозможно протестировать без мока сети — а именно он и содержит всю логику, которую стоит проверять.

**К чему обязывает:** новое поле из API теперь добавляется в двух местах — в `OrderDto` и в `toOrder()`. Забыть второе нельзя: TypeScript не соберётся.

### 2. Статус — один union вместо трёх булевых флагов

**Выбрал:**

```ts
// было
interface Order { isPaid: boolean; isShipped: boolean; isCancelled: boolean }

// стало
type OrderStatus = 'created' | 'paid' | 'shipped' | 'cancelled'
interface Order { status: OrderStatus }
```

**Почему:** три булева флага описывают восемь состояний, из которых реальных четыре. Остальные четыре — это не «редкие случаи», а состояния, которых не существует: отменённый и одновременно отгруженный заказ. Пока они выразимы в типе, каждый `if` обязан делать вид, что они возможны, и отсюда берутся ветки, которые никогда не исполняются. Union убирает их на уровне типа: невыразимое состояние невозможно собрать.

Это общая практика (make illegal states unrepresentable), в правилах проекта не записана.

**Отказался:** от того, чтобы оставить флаги и добавить рядом вычисляемый `status`. Два источника правды о том же самом расходятся ровно в тот день, когда кто-то поправит один и забудет второй.

**К чему обязывает:** новое состояние заказа = новый вариант union, и компилятор покажет все `switch`, которые его не разобрали. Раньше он молчал.

### 3. ViewModel получает зависимости аргументами, а не импортирует их

**Выбрал:** `new OrderListViewModel(ordersApi)` — API приходит в конструктор.

**Почему:** прямой импорт клиента внутрь ViewModel прибивает его к одной реализации гвоздями: в тесте его можно только перехватить мокингом модуля, то есть подменить не зависимость, а сам механизм импорта. Через аргумент — просто передал другой объект. Конвенция уже живёт в проекте: `billing/viewmodel/BillingViewModel.ts:22` собран так же.

**Отказался:** от DI-контейнера. На два модуля это инфраструктура ради инфраструктуры, а сборка руками в `modules/orders/index.ts` пока читается за десять секунд.

**К чему обязывает:** место сборки одно и явное. Если модулей станет заметно больше, а список аргументов длиннее пяти — вопрос контейнера открывается заново.

## Что осталось и где тонко

- **Ошибки загрузки показываются одной общей строкой.** ViewModel различает сетевую ошибку и 4xx, но UI пока схлопывает их в «не удалось загрузить». Сознательный срез: разговор про тексты ошибок не состоялся.
- **`OrderRow.tsx:8` — `TODO` про формат даты**, он был там до этой ветки. Про локаль, не про заказы; я его не трогал.
- **Пагинация осталась на старом пути** — она живёт в `OrderListPage.tsx` и ходит в API мимо ViewModel. Работает, но это второй канал к тем же данным, и следующий, кто добавит фильтр, споткнётся именно здесь.
- **Тестов на `toOrder()` нет.** Маппер — самая ценная для проверки часть ветки, и она сейчас не покрыта.

## Чего я не проверял

Тесты не гонял, приложение не запускал, с реальным бэкендом ответ не сверял — что `state` приходит именно теми четырьмя значениями, взято из типов в `api/types.ts`, не из живого ответа.

## Что я сжал

- **Состояние запроса в ViewModel** (`loading` / `error` / `data`) я описал одной строкой, а там есть нюанс с гонкой при быстром перелистывании — скажу, если интересно.
- **Почему маппер лежит в `viewmodel/`, а не в `domain/`** — есть аргументы в обе стороны, я взял тот, что уже принят в `billing`.
